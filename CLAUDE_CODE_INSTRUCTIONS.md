### Известные проблемы
1. **Размеры:** башни комично маленькие рядом с врагами. Причина почти наверняка в Pixels Per Unit: кадры врагов 64×64 при PPU 64 = 1 юнит (размер целой клетки), а у спрайтов башен видимая часть меньше / другой PPU. Масштаб ни разу системно не настраивался (автор попросил отложить).
2. **Уровень один и черновой:** путь и зоны расставлены руками в сцене.
3. В `LevelConfig` координаты: сетка 20×12, `tileSize = 1`, начало сетки = мировой ноль, центр клетки = `(x+0.5, y+0.5)` (`GridToWorld`). Пути начинаются с клетки за краем карты (`x = -1`).

## 2. Правила работы (обязательно)

1. **Сначала читать, потом писать.** Перед изменениями найди и прочитай реальные скрипты. Не создавай вторую систему, если похожая есть (карты — часть `LevelConfig`, а не отдельный `LevelLayout`).
2. **Одна задача — одна ветка/коммит.** Перед началом задачи попроси автора сделать коммит в GitKraken (или сам сделай `git add -A && git commit -m "..."`, если автор разрешил). Сообщения коммитов — на английском.
3. **Воспроизводимость важнее магии MCP.** Всё, что можно, автоматизируй **Editor-скриптами с пунктом меню** `Tools/Tower Defense/...` (как `LevelGenerator`). MCP используй, чтобы: осматривать сцену/префабы/импорт, запускать эти пункты меню, читать Console, проверять результат. Не строй карту «тайл за тайлом через MCP» — автор должен суметь повторить и объяснить это на защите.
4. **Не трогай `.meta`**, не переименовывай и не перемещай существующие ассеты без согласования — это рвёт ссылки в инспекторе. Файлы скриптов заменяй с тем же именем.
5. **Архитектура:** никакого GameManager-синглтона. Новые зависимости — через `Bootstrap`. Данные — в ScriptableObject. Визуальные компоненты не содержат игровой логики и только подписываются на события.
6. **После каждого изменения кода** дождись компиляции и проверь Console через MCP. Красные ошибки — чинить сразу.
7. **Play Mode проверяет автор.** В конце задачи дай короткий чек-лист «что запустить и на что посмотреть» и список ручных шагов в редакторе (куда кликнуть, какое поле заполнить) — автор новичок.
8. **Удаление** файлов/объектов сцены — только после явного «да» от автора.
9. Перед кодом коротко изложи план (3–7 пунктов) и дождись подтверждения, если задача затрагивает больше 3 файлов.

### Задача 1 — Размеры башен и врагов

**Стандарт масштаба (зафиксировать в `CLAUDE.md`):**

| Объект | Видимый размер, юниты |
|---|---|
| Клетка карты / зона строительства | 1.0 |
| Башня (основание) | 0.9–1.0 (заполняет зону) |
| Мечники | ~0.5 |
| Тяжёлый рыцарь | ~0.65 |
| Всадник (по длине) | ~0.75 |
| Снаряд | 0.15–0.25 |

Враги **меньше** башен — иначе закрывают их и выглядят как великаны.

**Подход:**
- Размер задаётся через **Pixels Per Unit** текстур, а не Scale префаба: у врагов один общий префаб, спрайт приходит из конфига; у башен масштаб корня исказил бы `RangeIndicator` и локальные позиции деталей.
- Напиши Editor-скрипт `Tools/Tower Defense/Normalize Sprite Sizes`: таблица «текстура/папка → целевой размер в юнитах», считает PPU по **видимой** ширине (alpha bounds, а не по холсту), выставляет PPU, Pivot Center, Filter Mode и делает `SaveAndReimport`. Таблицу держи в ScriptableObject или в константах скрипта — чтобы на защите было видно правило.
- Все кадры одного врага должны иметь **одинаковый** PPU (иначе анимация «дышит»).
- Детали башен (`cannon_turret`, трубачи, `bell_body` и т.д.) — тот же PPU, что у основания своей башни. После смены PPU проверь локальные позиции детей (`FirePoint (0.4, 0)`, `Flash`, `Dust (-0.25, 0)`) и предложи новые, если основание поменяло размер.
- Проверить и привести: Scale корней префабов `(1,1,1)`, `CircleCollider2D.radius` врага ≈ половина размера, `BoxCollider2D` башни ≈ `(0.9, 0.9)`, Scale объектов `Towers/Enemies/ProjectilePool` = 1.
- `Main Camera`: Orthographic, кадр вмещает сетку уровня (20×12 → центр `(10, 6)`, size ≈ 6.5 для 16:9). В Задаче 4 это станет автоматическим.

**Готово, когда:** на паузе в Scene view с включённой сеткой башня занимает клетку, враги заметно меньше, рыцарь крупнее мечника, всадник длиннее; радиусы башен не изменились.

### Задача 3 — Текстуры карты

**Что есть:** `MapTheme` (поля `grass`, `water`, `road`, `buildSlot`, `tree`, `rock`, `house`, `castleWall`), `MapBuilder` (слои Ground/Road/Decoration, не рисует поверх дороги и слотов), `LevelConfig.terrain` (прямоугольники Trees/Water/Rocks/Houses/CastleWall).

**Сделать:**
1. Найти пак Kenney в проекте. Если это тайлшит — нарезать 64×64 (PPU 64, Filter Point, Compression None). Если отдельные PNG — проверить PPU 64. Клетка = 1 юнит.
2. Установить `com.unity.2d.tilemap.extras` через `Packages/manifest.json` (подобрать версию, совместимую с 2023.2), дождаться импорта.
3. Editor-скрипт `Tools/Tower Defense/Create Map Theme`: создаёт Tile-ассеты в `Assets/Art/Map/Tiles`, **Rule Tile для дороги** (прямые, повороты, при наличии — Т-стыки) и заполняет `Assets/Configs/MapTheme_Default.asset`. Подбор конкретных тайлов Kenney — показать автору список/превью и согласовать (трава, дорога, вода, деревья, камни, дом/башенка, стена, площадка под башню).
4. Сцена: `Grid` (Cell Size 1, позиция `(0,0,0)`) с тремя Tilemap: Ground / Road / Decoration. Порядок отрисовки ниже всего игрового: например Sorting Layer `Map` или Order −30 / −20 / −10. Зоны строительства, башни, враги, снаряды — выше.
5. `MapBuilder` на `Grid`, назначить `LevelConfig` уровня 1 и `MapTheme`, выполнить **Build Map**.
6. Если `MapBuilder` не умеет углы воды/края — не усложнять, достаточно одиночного тайла; отметить как возможное улучшение.

**Готово, когда:** уровень 1 нарисован текстурами, дорога с корректными поворотами, декор не налезает на дорогу и слоты, по Gizmo (`LevelGizmoPreview`) путь совпадает с нарисованной дорогой.

> Важно: на этом шаге нарисованная дорога может **не совпасть** со старым `WaypointPath` и зонами в сцене — это нормально, исправляется в Задаче 4.

### Задача 4 — Уровни из LevelConfig в рантайме

**Цель:** `LevelConfig` становится единственным источником данных уровня: карта, путь(и), зоны строительства, экономика, волны.

**Дизайн (согласовать с автором после аудита):**
1. **Враги в волнах:** заменить `enum EnemyType` в `SpawnGroup` на `EnemyConfig enemy`. `LevelGenerator` находит конфиги врагов через `AssetDatabase` (по имени/папке) и перегенерирует 3 уровня. Если старые `WaveConfig` больше не нужны — пометить, но не удалять без согласия.
2. **`LevelLoader`** (обычный класс или MonoBehaviour-сервис, создаётся/связывается в `Bootstrap`), метод `Load(LevelConfig level)`:
   - `MapBuilder.Build(level)`;
   - строит пути: `WaypointPath` получает точки из `level.paths[i].waypoints` через `GridToWorld` (добавить в `WaypointPath` инициализацию из списка точек, не ломая ручной режим);
   - спавнит префаб `BuildZone` в каждой клетке `buildSlots` (родитель `BuildZones`, слой BuildZone, коллайдер 1×1);
   - передаёт `startingGold` / `startingLives` в `PlayerWallet` / `PlayerLives`;
   - передаёт волны и `timeBetweenWaves` в `EnemySpawner` (каждая группа — своя корутина с `delayBeforeGroup`; поддержать несколько путей для Castle Siege — индекс пути в `SpawnGroup` или чередование, смотри фактический `LevelConfig`).
   - подгоняет камеру под `gridSize` (`CameraFitter` или метод в загрузчике).
3. `Bootstrap` остаётся composition root: получает текущий `LevelConfig` (см. Задачу 5) и вызывает загрузку; логики в нём не прибавляется.
4. Удалить из игровой сцены ручные `Path` и `BuildZone_*` — **только после подтверждения автора** и после того, как уровень грузится из конфига.
5. Пересмотреть 3 уровня («черновой» уровень заменяется данными): проверить, что пути проходят по клеткам дороги, слоты не на дороге и стоят на поворотах/развилках, у River Crossing вода у южного края, у Castle Siege две дороги сходятся у ворот. Баланс (золото/волны) — первые прикидки, автор подкрутит после игры.

**Готово, когда:** при смене `LevelConfig` в `Bootstrap` и запуске игра полностью строится из ассета: карта, путь, зоны, деньги, жизни, волны. Все 3 уровня проходимы.

### Задача 5 — Переключение уровней

**Рекомендуемая схема (две сцены):**
- `MainMenu` — список из 3 уровней (кнопки с названием и описанием из `LevelConfig`). Простой View + Presenter, по аналогии с магазином — хорошо смотрится на защите.
- `Game` — текущая игровая сцена.
- `LevelCatalog` (ScriptableObject) — упорядоченный список трёх `LevelConfig`.
- Передача выбора между сценами: маленький статический `LevelSelection` с одним полем (индекс) **или** runtime-ScriptableObject. Объяснить автору компромисс (static проще и надёжнее при перезапуске Play Mode; SO нагляднее, но хранит состояние между запусками в редакторе). Не превращать это в GameManager.
- Перезагрузка сцены при смене уровня → чистое состояние (события, пул, кошелёк) без ручного сброса.
- Result panel в `HudView`: **Победа** → «Следующий уровень» (если есть) и «Меню»; **Поражение** → «Заново» и «Меню».
- Опционально: открытие уровней по прогрессу (`PlayerPrefs`, ключ с индексом последнего пройденного).
- Добавить обе сцены в Build Settings (через Editor-скрипт или MCP) и показать автору, где это проверить.
- Если в `Game` запускают без меню (Play прямо из сцены) — грузить уровень 1 по умолчанию.

**Готово, когда:** из меню запускается любой уровень, после победы переход на следующий, после поражения рестарт, возврат в меню работает, в Console нет ошибок и утечек подписок.
